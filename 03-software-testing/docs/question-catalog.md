## B01 - Test design: three-value BVA

**Question:** A form field accepts integer ages from 18 to 65 inclusive. Using three-value boundary value analysis as defined by ISTQB (each boundary of the valid partition together with both of its neighbouring values), how many distinct test inputs are needed? Give an integer.

**Answer:** `6`

**Reasoning:** The valid partition has boundaries 18 and 65. Three-value BVA takes each boundary and both neighbours: 17, 18, 19 and 64, 65, 66 - six distinct inputs.

**Designed shortcut:** Applying two-value BVA (17, 18, 65, 66). (gives `4`)

**Verification:** both (`verifiers.three_value_bva_count`)

**Sources:**
- ISTQB. Boundary Value Analysis white paper (2025) - Two-value and three-value BVA definitions, coverage formula and worked example for the range 6-15 <https://istqb.org/wp-content/uploads/2025/10/Boundary-Value-Analysis-white-paper.pdf>

## B02 - Test reliability: flaky suites

**Question:** A regression suite contains 300 independent tests. On a run where the product has no defect, each test passes with probability 0.995. What is the probability, as a percentage rounded to 1 decimal place, that the suite reports at least one failure on such a clean run?

**Answer:** `77.8`

**Reasoning:** P(all pass) = 0.995^300 = 0.2223, so P(at least one failure) = 1 - 0.2223 = 0.7777, i.e. 77.8%. Small per-test flakiness compounds across a large suite.

**Designed shortcut:** Reporting the per-test failure rate (0.5%) as the suite's failure rate. (gives `0.5`)

**Verification:** code (`verifiers.suite_failure_probability_pct`)

## B03 - Versioning: SemVer precedence

**Question:** Order these Semantic Versioning 2.0.0 version strings from LOWEST to HIGHEST precedence, giving them as a comma-separated list: 1.0.0-rc.1, 1.0.0-beta.11, 1.0.0, 1.0.0-alpha.beta, 1.0.0-beta, 1.0.0-alpha, 1.0.0-beta.2, 1.0.0-alpha.1

**Answer:** `1.0.0-alpha, 1.0.0-alpha.1, 1.0.0-alpha.beta, 1.0.0-beta, 1.0.0-beta.2, 1.0.0-beta.11, 1.0.0-rc.1, 1.0.0`

**Reasoning:** A release outranks its pre-releases. Pre-release identifiers are compared one by one: numeric identifiers compare numerically (2 < 11), numeric identifiers rank below alphanumeric ones (alpha.1 < alpha.beta), and a longer set outranks a shorter one when all earlier identifiers are equal (alpha < alpha.1).

**Designed shortcut:** Sorting the strings alphabetically, which puts 1.0.0 first and beta.11 before beta.2. (gives `1.0.0, 1.0.0-alpha, 1.0.0-alpha.1, 1.0.0-alpha.beta, 1.0.0-beta, 1.0.0-beta.11, 1.0.0-beta.2, 1.0.0-rc.1`)

**Verification:** both (`verifiers.semver_sorted`)

**Sources:**
- Semantic Versioning 2.0.0 - Item 11 (Precedence), including the example chain and the numeric-vs-alphanumeric rules <https://semver.org/>

## B04 - Test design: two-value BVA coverage

**Question:** Valid integer inputs are 6 to 15 inclusive. A test suite uses the inputs 5, 6, 10 and 15. Using ISTQB two-value boundary value analysis, what is the coverage, as a percentage rounded to 1 decimal place?

**Answer:** `75.0`

**Reasoning:** Two-value coverage items are each boundary and its closest neighbour in the adjacent partition: 5, 6, 15, 16. The suite exercises 5, 6 and 15; input 10 is not a coverage item and 16 is missing. Coverage = 3/4 = 75.0%.

## B05 - Test design: three-value BVA coverage

## B06 - API testing: duplicate JSON keys

**Question:** A JSON text contains the object {"id": 1, "id": 2}. According to RFC 8259 Section 4, what does the standard say the behaviour of software that receives such an object is? Answer with the single word the RFC uses.

**Answer:** `unpredictable`

**Reasoning:** RFC 8259 Section 4: 'The names within an object SHOULD be unique.' and 'When the names within an object are not unique, the behavior of software that receives such an object is unpredictable.' Parsers differ: some keep the last pair, some report an error, some keep all pairs.

**Designed shortcut:** Assuming the standard defines 'last value wins'; that is a common implementation behaviour, not a requirement. (gives `last value wins`)

**Verification:** source

**Sources:**

## B07 - Combinatorial testing: pairwise

**Question:** A system has 3 configuration parameters, each with 3 possible values. What is the minimum number of test cases needed so that every possible pair of values from any two different parameters appears together in at least one test? Give an integer.

**Answer:** `9`

**Reasoning:** Any two parameters have 3 x 3 = 9 distinct value pairs and one test covers exactly one pair for those two parameters, so at least 9 tests are needed. An orthogonal array such as (a, b, (a+b) mod 3) for a, b in 0..2 achieves 9 and covers all pairs for all three parameter pairs.

**Designed shortcut:** Answering 3 (one test per value) or 27 (exhaustive combinations). (gives `27`)

**Verification:** code (`verifiers.pairwise_minimum`)

## B08 - Test adequacy: mutation score

**Question:** A test suite is run against 56 generated mutants. Six of them are later shown to be equivalent mutants and the suite killed 42 mutants. Using the standard definition of mutation score from the mutation-testing literature, what is the score as a percentage rounded to 1 decimal place?

**Answer:** `84.0`

**Reasoning:** Mutation score = killed / non-equivalent mutants. Equivalent mutants cannot be killed by any test, so they are excluded: 42 / (56 - 6) = 42/50 = 84.0%.

**Designed shortcut:** Dividing by all generated mutants (42/56). (gives `75.0`)

**Verification:** both (`verifiers.mutation_score_pct`)

**Sources:**
- Jia Y, Harman M. An Analysis and Survey of the Development of Mutation Testing. IEEE Trans Softw Eng 2011 - Section II.B: 'The mutation score (MS) is the ratio of the number of killed mutants over the total number of non-equivalent mutants.'

## B09 - Flaky tests: confidence from reruns

**Question:** A test is suspected to be flaky with a true failure probability of 5% per run, runs being independent. What is the smallest number of consecutive passing runs n for which the probability of seeing n passes in a row, if the true failure probability really were 5%, is at most 5%? Give an integer.

**Answer:** `59`

**Reasoning:** Need 0.95^n <= 0.05, so n >= ln(0.05)/ln(0.95) = 58.4, hence the smallest integer is 59. (The 'rule of three' approximation 3/0.05 = 60 slightly overshoots.)

**Designed shortcut:** Using the rule-of-three approximation (60) instead of solving exactly. (gives `60`)

**Verification:** code (`verifiers.passes_needed`)

## B10 - Reliability: SLO error budget

**Question:** A service has a 99.9% availability SLO measured over a 30-day period (30 x 24 hours). How many minutes of downtime does the SLO allow in that period? Give the value rounded to 1 decimal place.

**Reasoning:** The period has 30 x 24 x 60 = 43,200 minutes. The error budget is 0.1% of that: 43.2 minutes.
